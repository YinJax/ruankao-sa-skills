# 考场主题分类

Use this reference when mapping a paper prompt to a topic family and choosing theory modules.

The catalog follows the classified essay-material pattern: chapter category -> subtopic -> theory basis -> argument points -> project application angles.

## 主题目录

| 大类 | 常见主题 | 模板模块选择 |
| --- | --- | --- |
| 开发方法 | 信息系统开发方法、软件开发模型、CBSE、软件过程改进 | 方法选择、过程组织、风险控制、复用与演进 |
| 架构设计 | 架构风格、架构评估、架构演化 | 质量属性、架构决策、评估权衡、演化机制 |
| 分布式与高并发 | 负载均衡、分布式事务、秒杀场景 | 并发压力、数据一致性、削峰限流、容错降级 |
| 面向服务架构 | SOA、微服务架构 | 服务拆分、接口契约、治理监控、独立部署 |
| 云原生架构 | 边云协同、可观测架构 | 弹性伸缩、容器化、日志指标链路、边云职责 |
| 测试与质量 | 系统测试、静态测试、动态测试、自动化测试、性能测试 | 质量目标、测试策略、缺陷闭环、性能验证 |
| 需求工程 | 需求分析、结构化分析、面向对象分析、DDD、需求获取 | 干系人、领域模型、需求边界、需求变更 |
| 系统设计 | 设计模式、基于架构的软件设计、面向对象设计 | 模块职责、对象关系、模式应用、扩展性 |
| 系统运维 | DevOps、运维管理、容灾恢复 | 发布流水线、监控告警、运维流程、恢复目标 |
| 数据与集成 | 数据集成、数据转换和迁移、大数据 | 数据口径、链路分层、迁移校验、批流处理 |

## 论点结构

每个主题优先生成 3 个核心论点。每个论点都按这个粒度组织：

- 理论定位：这个知识点解决什么架构或工程问题。
- 项目场景：用户项目中对应的业务约束、技术约束或风险。
- 个人动作：用户作为架构师做出的设计、评估、协调或落地动作。
- 权衡取舍：为什么选择该方案，舍弃了什么。
- 可验证结果：上线、性能、稳定性、质量、效率、成本、审计或用户反馈。

## 主题适配

- 题干要求具体技术时，模块必须覆盖该技术的机制、应用边界和风险。
- 题干要求管理或方法时，模块必须覆盖过程组织、参与角色和可交付物。
- 题干要求质量属性时，模块必须覆盖指标、架构策略和验证方法。
- 题干要求数据或集成时，模块必须覆盖口径、流向、转换规则和校验机制。

## 高频替换模块

These modules are reusable across recent prompts. Pick 3 that match the exact prompt.

| 方向 | 模块 1 | 模块 2 | 模块 3 |
| --- | --- | --- | --- |
| 分布式与高并发 | 流量入口与负载分担 | 一致性与幂等补偿 | 降级、熔断与故障恢复 |
| 数据与集成 | 数据源识别与模型统一 | 清洗转换与口径治理 | 数据质量、血缘与校验 |
| 测试与质量 | 质量目标与测试策略 | 测试设计与自动化执行 | 缺陷闭环与效果评估 |
| 云原生架构 | 资源弹性与自动化部署 | 可观测与高可用 | 安全合规与成本治理 |
| 面向服务架构 | 服务识别与拆分 | 接口契约与服务治理 | 复用、编排与演进 |
| 系统设计方法 | 模型/构件/对象识别 | 转换、组装或模式应用 | 可维护性与演化效果 |

## 论文主题卡

选题时先挑 1 个主主题，最多 1 个辅助主题。不要把所有主题都塞进同一篇模板。

| 主题 | 必写理论点 | 项目事实最低要求 | 常见硬套风险 |
| --- | --- | --- | --- |
| 架构设计 | 质量属性、架构风格、核心决策、评审与演化 | 有清晰系统边界、模块划分、关键质量目标和架构取舍 | 只画技术栈，不说明为什么这样设计 |
| 架构评估 | 评估目标、场景、权衡点、风险处置 | 有评审过程、备选方案、质量属性场景或风险清单 | 把评估写成上线总结，没有评估方法 |
| 可靠性 | 冗余、容错、降级、监控、恢复 | 有故障场景、可用性目标、恢复或告警措施 | 只写“稳定可靠”，没有故障和恢复证据 |
| 安全 | 身份认证、权限、审计、数据保护、合规 | 有用户/角色、权限边界、敏感数据或审计要求 | 只罗列安全产品，没有威胁和控制点 |
| 微服务/SOA | 服务拆分、契约、治理、编排、演进 | 有服务边界、接口协议、治理或独立部署事实 | 把普通分层系统硬写成微服务 |
| 云原生 | 容器化、弹性、自动化部署、可观测、成本治理 | 有部署环境、弹性伸缩、流水线或监控事实 | 只写用了云服务器，没有云原生机制 |
| 数据集成 | 数据源、模型统一、转换规则、质量校验 | 有多源数据、口径差异、同步链路或校验机制 | 只有数据库表，没有集成冲突 |
| 测试质量 | 质量目标、测试策略、自动化、缺陷闭环 | 有测试阶段、测试类型、缺陷处理或性能验证 | 把测试写成开发自测流水账 |
| DevOps 运维 | 流水线、发布、监控、告警、回滚 | 有部署发布、运维监控、故障处理或持续交付事实 | 只写“上线后运维”，缺少过程和工具链 |

每张主题卡生成模板时都要落到 3 段：

1. `理论点`：这类主题在考试里要说明的概念或方法。
2. `项目落点`：用户项目里能支撑这个理论点的事实。
3. `替换提醒`：考场题目变化时要替换的关键词、措施或结果。

## 不足时的处理

- 少于 3 个可辩护论点时，先给补充访谈问题。
- 项目事实只能支持相邻主题时，标为 `勉强支撑` 并给替代选题建议。
- 项目完全无法支撑题干时，不生成完整模板。
