# 模板工作流

1. 分材料：区分项目事实、题目材料和范文材料。
2. 拆题目或方向：有题目时读取 `prompt-obligation-patterns.md`，找出题目类型、限制词和必须回应的义务；没有题目时按通用可替换母版处理。
3. 访谈事实：只补模板需要的关键事实，不扩散到无关细节。
4. 建事实卡：把可辩护事实、待确认事实和风险分开。
5. 配模板：把事实映射到摘要、背景、论点卡、应用、总结五部分。
6. 检查覆盖：确认每个题干义务都能在模板里找到落点，并通过架构师视角检查。

## 输入材料门槛

生成完整模板前，至少要有这些事实：

- 项目时间：能判断是否满足用户要求的近三年约束。
- 项目背景：业务痛点、建设目标和干系人至少说清一项。
- 本人角色：用户未说明时，默认按“系统架构师/架构负责人”视角写；具体主导动作、职责边界和决策权限用 `[待本人确认]` 标出。
- 架构决策：至少 1 个与题目关键词直接相关的决策。
- 实施动作：至少 1 个用户参与或主导的落地动作。
- 结果证据：指标、验收、上线反馈、问题收敛或可观察变化至少一项。

默认追问优先级：

1. 项目时间。
2. 关键架构决策。
3. 真实结果。

不要默认追问“论文题目原文”和“本人角色”。没有题目时生成通用可替换母版；没有角色时默认系统架构师/架构负责人。

处理方式：

- 缺 1-2 项：可以生成模板，但对应位置标 `[待本人确认]`，并在风险里写明。
- 缺 3 项及以上：先问最多 5 个补充问题，不生成完整模板。
- 缺“具体论文题目”：可以生成通用可替换母版，不追问题目原文；在替换卡中标出考场拿到题目后必须改写的位置。
- 缺“本人角色”：默认架构师视角生成，但具体主导动作必须标 `[待本人确认]`。
- 缺“题目相关决策”：不生成完整专题模板，只给通用骨架、事实访谈问题和可用素材清单。

## 事实卡字段

- 项目时间：开始、上线、验收或关键阶段；用户要求近三年项目时，以用户提供的考试年份或日期为校验基准。
- 项目背景：业务痛点、建设目标、干系人、工期和投入。
- 个人角色：默认系统架构师/架构负责人；参与深度和主导动作不确定时标 `[待本人确认]`。
- 系统构成：核心功能、关键模块、外部系统、数据流。
- 主题素材：与题目相关的约束、决策、实施、权衡、结果。

## 架构师视角检查

每个核心段落都要能回答 5 个问题：

1. `约束是什么`：业务、质量属性、成本、工期、团队或技术边界。
2. `我判断了什么`：方案选择、风险识别、质量属性取舍或模块边界。
3. `我做了什么`：设计、评审、协调、落地、验证中的真实动作。
4. `我舍弃了什么`：备选方案、代价、风险或折中。
5. `结果怎么证明`：上线、验收、指标、故障收敛、反馈或可观察变化。

如果项目材料只有“用了某技术”，但没有判断、动作和结果，只能写成待补素材，不能当作完整论证。

## 生成原则

- 有具体题目时先适配题目，再套项目事实；没有题目时先生成通用母版，再标出题目替换位。
- 先保真，再追求完整。
- 不能支撑题目的项目，不硬造模板。
- 范文只能提供写作结构和论点路径，不能提供用户项目事实。

## 质量门

生成前确认：

- 摘要能说明项目时间、背景、目标、角色、技术要点和结果。
- 正文背景能交代项目基本信息、系统构成和团队角色。
- 每个题干义务都有对应段落，不把“论某技术”写成通用项目介绍。
- 理论部分至少有 3 张题目相关论点卡。
- 项目应用部分能说明理论如何落到真实场景。
- 总结同时包含正面效果和不足改进。

## 最小验收样例

| 输入情况 | 应输出 |
| --- | --- |
| 题目、项目时间、角色、决策、动作、结果都清楚 | 生成完整专题模板、覆盖矩阵、替换卡和质量检查 |
| 没有题目，但项目时间、背景、决策、动作、结果基本清楚 | 生成通用可替换母版、题目替换位、覆盖矩阵和质量检查 |
| 有项目背景和技术名词，但缺少角色、决策或结果 | 先问补充问题，只给可用素材和风险，不写完整模板 |
| 项目事实和题目关键词明显不匹配 | 输出“不建议套用”，给替代主题或补充事实方向 |
