# 理论准确性检查

Use this reference when diagnosing a draft that contains theory, definitions, method comparisons, named architecture styles, or process steps.

## 检查目标

判断理论部分是否既符合考试口径，又能承接用户项目事实。不要把它当官方评分细则；它只服务训练诊断。

## 检查项

| 项 | 看什么 | 常见问题 | 修复动作 |
| --- | --- | --- | --- |
| 定义边界 | 是否说明概念解决什么问题、适用什么范围 | 只背定义，和题目关键词脱节 | 改成“定义 + 解决的问题 + 本文讨论边界” |
| 分类或原则 | 是否列出题目要求的类型、原则、步骤或活动 | 只写一个技术点，漏掉题干要求的“有哪些/区别” | 补 3 个以内核心分类或原则 |
| 对比维度 | 题干要求区别、选择、评估时是否有维度 | 只说 A 好 B 不好 | 按目标、质量属性、活动、成本、风险对比 |
| 适用边界 | 是否写清适合和不适合的场景 | 把技术写成万能方案 | 补适用条件、限制和替代方案 |
| 项目承接 | 理论后是否接到项目约束、动作和结果 | 理论一大段，项目只有一句 | 每个论点补“项目场景 -> 架构师动作 -> 验证结果” |

## 高风险信号

- 名词很多，但没有任何架构取舍。
- 理论段和项目段能互换到任何题目。
- 题干要求“比较/区别/评估”，正文没有对比维度。
- 题干要求“应用/实施/效果”，正文没有真实项目动作和结果。
- 使用具体方法名，如 ATAM、WPDRRC、Lambda/Kappa、DAO/DTO/ORM，却写错步骤、层次或适用场景。

## 输出片段

```text
理论准确性检查：
- 准确：哪些定义、分类或方法步骤基本可靠。
- 偏薄：哪些只是教材定义，缺少边界、对比或项目承接。
- 风险：哪些概念可能误用、硬套或与题干义务不匹配。
- 修复：按“定义边界 -> 分类/原则 -> 项目落点 -> 取舍验证”改写。
```
