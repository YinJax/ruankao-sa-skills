# 案例分析答题工作流

## 先读问题

优先读每个「问题」而不是从背景第一行开始精读。先判断题目在问：

- `说明/简述/分析`：需要概念 + 场景作用 + 后果。
- `设计/提出方案`：需要组件、流程、策略、保障措施。
- `比较/是否合理`：需要结论、理由、适用条件、风险。
- `填空/补图/补表`：需要从题干术语、上下游关系、质量属性词中找线索。
- `故障原因/改进措施`：需要把现象映射到根因，再给闭环措施。

## 题干标注

把题干压缩成四类线索：

| 线索 | 作用 | 常见触发词 |
|---|---|---|
| 业务目标 | 决定质量属性 | 高并发、低延迟、快速迭代、合规、容灾 |
| 故障现象 | 对应原因分析 | 超时、雪崩、数据不一致、越权、单点故障 |
| 技术现状 | 决定改造边界 | 单体、微服务、Redis、Kubernetes、Eureka、网关 |
| 约束条件 | 决定取舍 | 成本、实时性、强一致、敏感数据、跨系统 |

## 分问作答

每问用「结论句 + 依据 + 措施 + 效果/代价」四段式。

```text
结论：本问应采用/不宜采用 X。
依据：题干出现 A、B、C，说明核心矛盾是 Y。
措施：从组件、流程、策略、监控和容错五个角度落地。
效果/代价：解决 Z，但会带来复杂度、成本、延迟或一致性权衡。
```

## 题型选择策略

在 4 选 2 题中，先判断这题是否能拿保底分。

| 题型 | 优先级 | 保底分来源 | 谨慎点 |
|---|---|---|---|
| 质量属性/架构评估 | 高 | 属性判断、场景六要素、策略措施 | 不要只背定义 |
| Redis/缓存/高并发 | 高 | 问题识别、原因、治理措施 | 注意一致性和补偿 |
| 微服务治理 | 高 | 注册发现、限流熔断、监控链路 | 不要只写组件名 |
| 数据库/数据一致性 | 高 | 事务、隔离、备份恢复、读写分离 | 不要把最终一致写成强一致 |
| UML/建模 | 中 | 元素识别、关系、图形规则 | 题干名词动词要对应 |
| 安全权限 | 中 | 认证、授权、加密、审计 | 不要脱离敏感数据场景 |
| DevOps/云原生 | 中 | 流水线、容器、监控、回滚 | 不要只写工具名 |
| 陌生产品/版本细节 | 低 | 通用架构原则 | 不要编产品特性 |

谨慎选择：

- 全是陌生名词定义、没有题干线索的题。
- 需要特定产品版本细节的题。
- 架构图元素无法建立上下游关系的题。

时间紧张时，优先选能写出 3 个以上明确措施的题。

## 考场答案形态

- 使用短句分点，避免论文式大段叙述。
- 每点尽量包含一个关键词和一个题干场景。
- 不确定时写通用架构原则：解耦、冗余、隔离、限流、降级、监控、审计、数据校验。
- 时间紧张时优先写高价值动词：识别、隔离、重试、补偿、缓存、加密、授权、监控、告警、扩容。
